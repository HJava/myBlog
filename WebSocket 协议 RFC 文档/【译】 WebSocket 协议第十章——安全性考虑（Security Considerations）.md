## 10 安全性考虑（协议正文）

这一章描述了一些 WebSocket 协议适用的安全性考虑。这一章的小节描述了这些特定的安全性考虑。

### 10.1 非浏览器客户端

WebSocket 协议防止在受信任的应用例如 Web 浏览器中执行的恶意 JavaScript 代码，例如通过检查`Origin`头字段（见下面）。见第 1.6 节去了解更多详情。这种假设在更有能力的客户端的情况下不成立。

这个协议可以被网页中的脚本使用，也可以通过宿主直接使用。这些宿主是代表自己的利益的，因此可以发送假的`Origin`头字段来欺骗服务端。因此服务端对于他们正在和已知的源的脚本直接通信的假设需要小心，并且必须考虑到他们可能会被以没有预期的方式访问。特别地，服务端不应该相信任何输入都是有效的。

示例：如果服务端使用输入的内容作为一部分的 SQL 查询语句，所有的输入文本都应该在传递给 SQL 服务器之前进行转义，以免服务端受到 SQL 注入攻击。

### 10.2 源考虑

只处理特定站点，不打算处理任意 Web 页面输入数据的服务器应该验证`Origin`字段是否是他们预期的。如果服务端收到的源字段是不接受的，那么它应该用一个包含 HTTP 403 Forbidden 状态码的响应作为 WebSocket 握手的响应。

当不信任的一方是 JavaScript 应用作者，并且该应用在受信任的客户端中运行时，`Origin`字段可以避免出现这种攻击的情况。客户端可以连接到服务端，通过协议中的`Origin`字段，确定是否开放连接的权限给 JavaScript 应用。这么做的目的不是阻止非浏览器应用建立连接，而是保证在受信任的浏览器中可能运行的恶意 JavaScript 代码并不会构建一个假的 WebSocket 握手。

### 10.3 基础设施攻击（添加掩码）

除了终端可能会成为通过 WebSocket 被攻击的目标之外，网络基础设施的另外一部分，例如代理，也有可能是攻击的对象。

在这个协议的开发过程中，通过一个实验验证了一类针对代理的攻击，这类攻击会导致实际部署的缓存代理被投毒。一般形式的攻击就是建立一个与攻击者控制的服务端的连接，实现一个与 WebSocket 协议建立连接相似的 HTTP UPGRADE 连接，然后通过升级以后的连接发送数据，看起来就像是针对已知的特定资源（在攻击中，这可能类似于广泛部署的脚本，用于跟踪广告服务网络上的点击或资源）进行 GET 请求。远端服务器可能会通过一些看上去像响应数据的内容来响应假的 GET 请求，然后这个响应就会被一定比例（非零）的已部署中介缓存下来，因此导致缓存投毒。这个攻击带来的影响就是，如果一个用户被诱导访问了一个攻击者控制的网站，那么攻击者可以针对这个用户以及使用相同缓存的其他用户进行缓存投毒，并在其他源上运行恶意脚本，破坏 Web 安全模型。

为了避免对中介服务的此类攻击，仅使用不符合 HTTP 的帧格式为应用程序的数据添加前缀是不够的，我们不可能详细的检查和测试每一个不合标准的中介服务有没有跳过这种非 HTTP 帧，或者对帧载荷处理不正确的情况。因此，采用的防御措施是对客户端发送给服务端的所有数据添加掩码，这样的话远端的脚本（攻击者）就不能够控制发送的数据如何出现在线路上，因此就不能够构造一条被中介误解的 HTTP 请求。

客户端必须为每一帧选择一个新的掩码值，使用一个不能够被提供数据的终端应用预测到的算法。例如，每一个掩码值可以通过一个加密强随机数生成器来生成。如果相同的值已经被使用过或者已经存在一种方式能够判断出下一个值如何选择时，攻击者可以发送一个添加了掩码的消息，来模拟一个 HTTP 请求（将攻击者希望在线路上看到的消息，用下一个将被使用的掩码值预先添加掩码，那么当客户端使用这个掩码值时，实际上就会对数据反掩码）。

一旦客户端开始传输一个帧，这个帧的有效载荷（应用程序提供的数据）就不能够被客户端应用程序修改，这个策略是很重要的。否则，攻击者可以发送一个都是已知值（例如全部为 0）的初始值的很长的帧，计算收到第一部分数据时使用过的掩码，然后修改帧中尚未发送的数据，以便在添加掩码时显示为 HTTP 请求。（这与我们在之前的段落中描述的使用已知的值和可预测的值作为掩码值，实际上是相同的问题。）如果还需要发送另外的数据，或者要发送的数据有所改变，那么新的数据或者修改的数据必须使用一个新的数据帧进行发送，因此也需要选择一个新的掩码值。简短来说，一旦一个帧的传输开始后，内容不能够被远端的脚本（应用）修改。

受保护的威胁模型是客户端发送看似HTTP请求的数据的模型。因此，从客户端发送给服务端的频道数据需要添加掩码值。从服务端到客户端的数据看上去像是一个请求的响应，但是，为了完成一次请求，客户端也需要可以伪造请求。因此，我们不认为需要在双向传输上添加掩码。（服务端发送给客户端的数据不需要添加掩码）

尽管通过添加掩码提供了保护，但是不兼容的 HTTP 代理仍然会受到不添加掩码的客户端和服务端发起的这种类型的投毒攻击。

### 10.4 指定实现的限制

如果实现对帧大小或者从多个帧重新组装后的消息总大小有实现或平台相关的限制，那么它必须保护自己不超过这些限制。（例如：一个恶意的终端可能会尝试耗尽对端的内存或者通过发送一个大的帧（例如：大小为 2 \*\* 60）或发送一个长的由许多分片帧构成的流来进行拒绝服务攻击）。这些实现应该对帧的大小和组装过后的消息的总大小有一定的限制。

### 10.5 WebSocket 客户端认证

这个协议在 WebSocket 握手时，没有规定服务端可以使用哪种方式对客户端进行认证。WebSocket 服务器可以使用任意 HTTP 服务器通用的认证机制，例如： Cookie、HTTP 认证或者 TLS 认证。

### 10.6 连接保密性和完整性

连接的保密性和完整性是通过在 TLS 之上运行 WebSocket 协议（wss 的 URLs）来提供的。WebSocket 协议实现必须支持 TLS，并且应该在与对端进行数据传输时使用它。

如果在连接中使用 TLS，TLS带来的连接的收益非常依赖于 TLS 握手时的算法的强度。例如，一些 TLS 的加密算法不提供连接保密性。为了实现合理等级的保护措施，客户端应该只使用强 TLS 算法。“Web 安全：用户接口指南”（[W3C.REC-wsc-ui-20100812][11]）讨论了什么是强 TLS 算法。[RFC5246][12] 的[附录 A.5][13]和[附录 D.3][14]提供了另外的指导。

### 10.7 处理无用数据

传入的数据必须经过客户端和服务端的验证。如果，在某个时候，一个终端面对它无法理解的数据或者违反了这个终端定义的输入安全规范和标准，或者这个终端在开始握手时没有收到对应的预期值时（在客户端请求中不正确的路径或者源），终端可以断开 TCP 连接。如果在成功的握手后收到了无效的数据，终端应该在进入`关闭 WebSocket 连接`流程前，发送一个带有合适的状态码（第 7.4 节）的关闭帧。使用一个合适的状态码的关闭帧有助于诊断这个问题。如果这个无效的数据是在 WebSocket 握手时收到的，服务端应该响应一个合适的 HTTP 状态码（[RFC2616][15]）。

使用错误的编码来发送数据是一类通用的安全问题。这个协议指定文本类型数据（而不是二进制或者其他类型）的消息使用 UTF-8 编码。虽然仍然可以得到长度值，并且实现此协议的应用程序可以使用这个长度来确定帧实际结束的位置，但是发送编码不正确的数据仍然可能会打破基于此协议构建的应用程序所做的假设，导致从数据的错误解释到数据丢失或潜在的安全漏洞等各种问题。

### 10.8 在 WebSocket 握手中使用 SHA-1

在这个文档中描述的 WebSocket 握手协议不依赖任意 SHA-1 的安全属性，例如抗碰撞性和对第二原像攻击的抵抗力（就像 [RFC4270][16] 描述的一样）。
